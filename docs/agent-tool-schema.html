Version and authority

AuditOps v2.2 is an additive text-agent revision. Existing v2.1 contracts and artifacts remain unchanged. New tasks, prompts, benchmarks, runs, and reports receive v2.2 identities.

The committed JSON Schemas, Python validators, operation registry, and deterministic verifier are normative. This page explains those interfaces; it does not replace them.

Scope boundary. A released result verifies a calculation or an extractive statement against frozen public-filing evidence. It is not an audit opinion, a statutory audit, professional judgment, fraud or going-concern work, or assurance that the source filing is truthful or complete.

Each text task binds to exactly one operation, argument schema, observation schema, terminal output schema, and refusal policy. Every runtime consumer reads this registry; task-specific routing is not duplicated.

A task with no tool, multiple tools, the wrong tool, an unknown output schema, or a mismatched output schema is rejected before model inference. The model cannot register an operation or alter its arguments.

AgentTaskInputV2.2

The model-visible task contains only sanitized task, jurisdiction, framework, standards, entity, filing, period, operation, and closed evidence-scope data. Unknown properties and evaluation-only names such as gold, target, expected_value, and is_answerable fail validation.

Versionagent_task_input_version is v2.2.

Evidence provenanceselection_method is TYPED_FACT_MATERIALIZATION or FROZEN_BM25.

Evidence and ContextPackV2.2

Closed evidence

  • Every evidence ID exists, is unique, and belongs to an allowed filing.
  • Ordering is stable and complete; the runtime never clips an ID or source descriptor.
  • Quantitative evidence retains period, unit, context, dimensions, and taxonomy provenance.
  • Narrative evidence retains source location and the exact extractive text used for claims.

Stateless context

  • At most five items enter one case-local context.
  • BM25 retrieval uses candidate_k=15 and frozen stable ordering.
  • Narrative planning hides chunks; the load observation exposes the frozen scope once at synthesis.
  • The model context is 16,384 tokens and prompt-visible input is capped at 14,336.
  • An indivisible valid context that does not fit returns CONTEXT_OVERFLOW.
No hidden memory layer. There is no vector database, cross-case memory, autonomous swarm, or LLM context summarizer. Context construction is deterministic and its complete ordered form is hash-bound.

AgentProposalV2 action invariants

The public proposal remains a strict discriminated union. Inference uses smaller stage- and task-specific schemas: planning permits only the exact CALL_TOOL; direct, synthesis, and repair permit only terminal actions bound to the current task, period, unit, refusal codes, and evidence IDs. The runtime fills only invariant null and advisory fields when normalizing into AgentProposalV2.

ActionRequired fieldsForbidden or fixed fields
CALL_TOOL Registered tool_name and exact tool_arguments. Final answer, refusal, citation, claim, value, unit, and period fields are null or empty; model_uncertainty=NONE; model_escalation_requested=false.
ANSWER status=OK and the exact task period. Quantitative output uses a canonical fixed-point decimal string and exact unit. A narrative model returns only one to three {evidence_id, exact_quote} extracts. No model-authored narrative prose is released. The runtime derives answer text, claims, and citations from contiguous quotes; paraphrases, forged IDs, and duplicate extracts fail closed.
REFUSE status=REFUSAL, the exact task period, and a registered refusal code. No tool, value, unit, answer text, citations, or claims.

model_uncertainty (NONE, LOW, or HIGH) and model_escalation_requested are advisory telemetry only. They never change verification, release, repair, or terminal routing.

Canonical output matters. Numerically equal spellings such as 2, 2.0, and 2e0 are not interchangeable v2.2 outputs. One canonical value and exact unit produce one stable audit identity. Narrative generation is bounded to three exact extracts.

ToolObservationV2.2 and deterministic execution

Metric observation

evaluate_metric_spec runs only a registered formula over frozen typed facts. Its observation binds status, value, unit, period, input evidence, and calculation provenance.

Frozen-evidence observation

load_frozen_evidence returns retrieval_status=SCOPE_LOADED, answerability_assessed=false, the ordered frozen top-five chunks, scope hash, selection provenance, and typed empty reason. It does not imply support, search a live corpus, or discover evidence.

The strict observation union records whether an observation was model-visible or verifier-only. The verifier recomputes or replays the registered operation independently; a mismatch is an integrity failure, not an ordinary model or infrastructure error.

Local verifier states and terminal case outcomes

Verifier dispositions describe a local gate decision. Case outcomes describe the one terminal result emitted by the runtime. The two vocabularies are intentionally separate.

ContractVocabularyMeaning
VerifierResultV2.dispositionTOOL_CALL_APPROVED, REPAIR_REQUIRED, RELEASED, SAFE_REFUSAL, FAILEDA stage-local gate state retained in the verifier trace.
AgentCaseResultV2.outcome
AgentRunRecordV2.outcome		RELEASED, SAFE_REFUSAL, MODEL_FAILURE, INFRASTRUCTURE_FAILURE, INTEGRITY_FAILUREThe final, externally visible case class. Transient verifier states cannot appear here.

Repair policy

  • Malformed JSON, schema/action-shape errors, and canonical lexical-format errors may receive one repair.
  • Target-sensitive, evidence, arithmetic, refusal, cross-task, observation-binding, prompt-injection-policy, and integrity errors are non-repairable.
  • A repair prompt contains only allowlisted safe diagnostics. If none remain, the case ends as MODEL_FAILURE without invoking or consuming a repair.
  • One case receives at most one repair. A failed repair is terminal and a second repair cannot be requested.
Safe refusal is not necessity. SAFE_REFUSAL means the refusal is policy-safe to expose. Whether it was necessary, or was an over-refusal, is scored offline against evaluator-only gold.

Portable identity and complete request binding

All hash-bearing data uses auditops.canonical_json.v1: compact sorted-key JSON, UTF-8 text, no NaN or infinity, and string object keys only. This is a versioned AuditOps Python canonicalizer; it is not RFC 8785/JCS.

Each model attempt records request_sha256 and response_schema_sha256. The request hash binds the stage, repair attempt, ordered messages, full response schema, output cap, sampling, seed, prompt version, and portable semantic model configuration.

AgentRunRecordV2.2 additionally binds the narrative subtype, exact demonstration pack, and metric-operation contract. It records initialization, generation, and tool timing separately. The runtime derives run_id only after context construction.

The portable model identity includes model ID, revision, quantization, backend, context/input/output caps, normalized sampling, seed, thinking mode, and chat-template hash. Deployment identity additionally binds the local model path; the path never changes the portable semantic run ID.

IMPLEMENTED

VLM diagnostics use separate contracts

vlm_diagnostic is not a text-agent task and is rejected by the v2.2 text runtime. Image-PDF work enters the separate VlmDiagnosticTaskV1 and VlmDiagnosticResultV1 contracts and existing VLM runtime. Its extraction and page-citation results remain outside the XHTML/text benchmark score.

PROPOSED

Possible extensions require a new decision

Cross-language replay may justify a standards-conforming canonicalization profile later. Until then, implementations must identify the AuditOps Python canonicalizer and must not claim JCS compatibility.

DEFERRED

Not part of v2.2

Human escalation workflows, audit opinions, professional-judgment conclusions, fine-tuning, vector retrieval, multi-agent swarms, live model tools, and merging VLM results into the text benchmark are deferred. No ESCALATED terminal outcome exists without an approved human workflow.
